#ABSTRACT#
#P#The Advanced Subscription and Membership Platform is a full-stack web application that lets individual content creators run their own paid membership space and lets audiences subscribe to a specific creator rather than to a single central catalogue. The purpose of the project is to give creators direct control over what they publish, how they price access, and who can open each item, while giving subscribers a clear path from free browsing to paid membership. Existing membership services usually place every creator inside one shared system, apply one fixed set of rules, and take a share of each payment. This arrangement limits how a creator organises tiers and separates one creator's audience from another. The gap this project addresses is the lack of a self-contained, per-creator membership model where access is decided for each creator independently and where the billing flow stays simple and auditable.
#P#The system is built with Next.js 15 and React 19 using TypeScript, with Clerk for authentication, PostgreSQL for all persistent data, Stripe for recurring billing through hosted Checkout and the Customer Portal, and Cloudflare R2 for file storage. It supports three roles. A subscriber can follow a creator for free or pay for a Basic or Premium tier, then open gated videos, articles, and downloadable files within a monthly download quota. A creator publishes content, sets tiers, and reviews subscribers, revenue, and analytics. An administrator oversees users, content, payments, and platform settings. Access for every item is compared against the subscriber's tier for that creator, and paid access is written to the database only after Stripe confirms payment through a signed webhook.
#P#The platform was checked with manual black-box and functional testing performed by using the running application on a standard development machine. Each major workflow was exercised by hand, including sign-up and verification, following a creator, paying for a tier through Stripe test mode, downloading files against the quota, cancelling a paid plan, and administrative actions such as suspending an account. The observed behaviour matched the expected behaviour for the tested cases, which confirmed that the access rules, the billing flow, and the role restrictions work together as designed.
#P#The project has clear limits. It runs against Stripe test mode and a single database, it has no automated test suite, and it does not include creator payouts or a platform-wide plan that unlocks every creator at once. Future work can add an automated testing layer, extend analytics, introduce creator payout handling, and prepare the application for production hosting. Even with these limits, the system shows a complete and working per-creator membership model from sign-up through paid access and administration.

#TITLE#CHAPTER 1#INTRODUCTION
#P#The way people pay for online content has changed. Instead of buying a single file once, audiences now pay a recurring fee to support the people who make videos, write articles, and share downloadable material. This model, often called the creator subscription economy, rewards steady output and a direct relationship between a maker and the people who follow the work. Several large services proved that the idea works at scale, but most of them were built around one central catalogue and one company that keeps a share of every payment. A creator who joins such a service accepts its rules, its cut, and its way of grouping members. That trade-off is acceptable for some, yet it leaves little room for a creator who wants a private space with pricing and access under their own control.
#P#The Advanced Subscription and Membership Platform was built to study and solve a narrower version of this problem. It gives each creator a separate space where they publish their own videos, articles, and files, and it lets a subscriber pay that specific creator for access rather than paying the site as a whole. A person can follow a creator for free, or move up to a paid tier when they want more. The platform tracks who can open each item, collects payments through Stripe, stores files on cloud object storage, and gives administrators the tools to keep the service healthy. Compared with a single global catalogue, this per-creator design keeps each creator's audience, pricing, and content separate, which makes the membership relationship easier to reason about and easier to control.
#H1#1.1 Project Domain
#P#This project sits in the domain of full-stack web development applied to subscription and membership management for digital content. It brings together several areas that usually sit apart. It handles user authentication and role management, recurring billing, access control based on paid tiers, and cloud file storage, and it presents all of this through a web interface backed by server-side application logic. The central problem in this domain is controlled access to paid digital content. A creator uploads material and marks how much access each item needs, and the platform must make sure that only subscribers with the right tier can open or download that material, while still letting the public see previews. The domain therefore combines billing correctness with careful permission checks, because a mistake in either area either blocks a paying member or exposes paid content to someone who has not paid. The project title matches this domain directly, since the system is an advanced subscription and membership platform whose main concern is who may access what, and on what terms.
#P#Work in this domain has to respect the boundary between the code that runs in the browser and the code that runs on the server. Anything sent to the browser can be read or changed by the user, so an access decision that only hides a button is not a real control. For this reason the project places every access check on the server and treats the browser only as a way to show results and collect input. It also has to work with services it does not own, since authentication, payment, and storage are provided by outside companies. This means the design must handle events that arrive from those services and must stay correct even when a call to one of them is slow or fails, which shapes many of the decisions described later in this report.
#H1#1.2 Problem Identification
#P#Creators who want to earn from their work face problems that current tools solve only in part. Popular membership services place every creator inside one large system, take a percentage of each payment, and often group members using a structure the creator cannot fully change. A creator on such a service cannot easily keep their audience separate from everyone else's, and the payment rules are fixed by the host. On the technical side, building a membership site from scratch means solving authentication, recurring billing, file protection, and access control at the same time, and getting any one of these wrong causes real harm. If billing state and access state drift apart, a member who has paid may be locked out, or a member who has stopped paying may keep access. If files are served directly, a shared link can leak paid material to people who never subscribed. These issues explain why a smaller, self-contained membership model, with clear per-creator access rules and a billing flow that only grants access after payment is confirmed, is worth building and studying.
#H2#1.2.1 Proposed Solution
#P#The proposed solution is a web application where each creator owns a membership space and each subscriber holds a separate relationship with every creator they join. When a subscriber follows a creator for free, the system records a free membership for that pair. When a subscriber pays for Basic or Premium, the system starts a Stripe Checkout session, and it grants paid access only after Stripe confirms the payment through a signed webhook. Every piece of content carries a required tier, and the server compares that tier against the subscriber's current tier for the owning creator before it serves the item. Files are never handed to the browser as public links; instead they are streamed as attachments after an access check, and downloads are counted against a monthly quota. Administrators sit above these flows and can suspend accounts, cancel or reactivate subscriptions through Stripe, refund or retry payments, and place the whole site in maintenance mode. This design keeps billing and access tightly linked and keeps each creator's membership separate from the rest.
#H2#1.2.2 Objectives
#OBJ#To design a per-creator subscription model where access is decided separately for each creator and tier.
#OBJ#To develop secure authentication and role handling for subscribers, creators, and administrators.
#OBJ#To integrate recurring billing through Stripe so that paid access is granted only after payment is confirmed.
#OBJ#To protect paid files by serving them as access-checked attachments and by enforcing a monthly download quota.
#OBJ#To provide creators with tools to publish content, manage tiers, and review subscribers, revenue, and analytics.
#OBJ#To validate the developed system through manual functional testing of its main workflows.
#H2#1.2.3 Scope of the Project
#P#The system covers the full membership cycle for digital content. It allows a visitor to register, verify an email, and sign in, and it supports Google sign-in and password reset. It lets a subscriber browse public creator pages, follow a creator for free, and pay for a Basic or Premium tier through Stripe Checkout. It gives a subscriber a library of gated videos, articles, and files, a subscription page, access to the Stripe Customer Portal, an account area, and an in-app notification inbox. It gives a creator a workspace to publish video, article, and file content, to set Free, Basic, and Premium tiers, and to view subscribers, revenue, and analytics. It gives an administrator control over users, creators, content, plans, subscriptions, payments, notifications, and platform settings. The system runs as a web application intended for desktop and mobile browsers. It works against Stripe test mode and a single PostgreSQL database, and it does not handle creator payouts or a single plan that unlocks every creator at once.
#H1#1.3 Effectiveness / Usefulness of the System
#P#The system is useful because it keeps the membership relationship simple and safe for both sides. A creator gains a private space with three clear tiers and direct control over what each tier unlocks, without sharing a catalogue with unrelated creators. A subscriber gains a clear route from free following to paid access, with a familiar and trusted payment screen provided by Stripe, and with a record of downloads that keeps usage fair. Because access is always checked on the server and paid access is only written after Stripe confirms a payment, the system avoids the common failure where billing and access fall out of step. The download quota and attachment-only file delivery reduce the risk of paid material spreading through shared links. For a learner or a small creator, this makes the platform a practical starting point, and for the purpose of this project it shows how billing, authentication, storage, and access control can be combined into one coherent service.
#P#The tier design also keeps the offer easy to understand. The Free tier costs nothing and is reached by following a creator, and it allows a small number of file downloads each month along with free articles and video previews. The Basic tier is a paid monthly plan that opens the free and basic content and raises the monthly download limit. The Premium tier is a higher paid plan that opens every tier of content from that creator and removes the download limit. Because these three levels apply per creator, a subscriber can hold a different tier with each creator they join, which mirrors how people support different makers by different amounts. This clarity is part of what makes the system practical for real use rather than only as an academic exercise.

#TITLE#CHAPTER 2#BACKGROUND AND EXISTING SYSTEMS
#P#The problem under consideration is how a single platform can host many independent creators while keeping each creator's paid content, pricing, and audience separate and secure. This chapter looks at the background of that problem and the systems that already try to solve parts of it.
#P#The chapter is organised into four sections. Section 2.1 reviews related literature on access control, software-as-a-service architecture, and subscriber retention and analytics. Section 2.2 discusses existing membership systems and their strengths and weaknesses. Section 2.3 states the problems identified from that existing work, and Section 2.4 defines the boundary chosen for the proposed solution.
#H1#2.1 Related Literature Review
#P#The first area of related work is access control, which decides who may perform which actions in a system. Sandhu, Coyne, Feinstein, and Youman (1996) set out a family of role-based access control models in which permissions are attached to roles and users are then assigned to those roles rather than being granted rights one by one. This idea maps directly onto the present project, which defines the roles of subscriber, creator, and administrator and gives each role its own set of actions. The same model also supports the per-item access rule, since the required tier on a content item acts as the permission that a subscriber's role and tier must satisfy before the server serves the item. Basing the design on an established access control model gives the permission structure a firm footing rather than an informal one.
#P#The second area is the architecture of software that serves many customers from one running system, often called software as a service. Chong and Carraro (2006), in a Microsoft technical publication, describe how such software should be configurable, efficient across many tenants, and able to scale as the number of users grows. This is relevant because the platform hosts many independent creators inside one application and one database, and it must keep each creator's space separate and configurable while sharing the same code and infrastructure. Their treatment of multi-tenant design supports the choice to separate per-creator data by ownership within shared tables rather than to run a separate system for each creator. Because this source is an industry technical paper rather than a peer-reviewed study, it is treated as practical architectural guidance rather than as experimental evidence.
#P#The third area is subscriber retention and the analytics used to understand it. Ascarza (2018), writing in the Journal of Marketing Research, uses field experiments and machine-learning methods to show that aiming retention effort at the customers most likely to leave can be ineffective, and that the value of a retention action depends on how a customer responds to it rather than on churn risk alone. This finding gives a reason for the platform to collect engagement and subscription analytics for creators, since sound retention decisions need evidence about how subscribers actually behave. The present project does not build a retention model, so this source supports the rationale for the analytics feature rather than a particular algorithm.
#P#These three sources cover access control, service architecture, and retention analytics, which are the areas where existing research maps cleanly onto the project. Two further objectives, namely recurring payment handling and automated renewal notifications, are engineering concerns that this project meets by following the official documentation of the payment provider rather than a research paper, since these are matters of correct integration rather than open research questions. Section 2.2 therefore turns to existing systems to compare how these payment and membership features are offered in practice. Table 2.1 summarises the three reviewed sources.

#H1#2.3 Identified Problem from Existing Work
#P#The systems above show two repeating limits. First, most of them place every creator inside one central catalogue and apply one fee and one set of grouping rules, which reduces a creator's control over pricing and over how their audience is kept separate from others. Second, several tools are shaped around a single content type, such as newsletters or tips, rather than a mixed library of videos, articles, and files where each item can carry its own required tier. There is also a technical concern that runs through this space, which is keeping billing state and access state in step so that a paying member is never wrongly locked out and a non-paying user never keeps access. From these observations, the improvement this project targets is a self-contained per-creator membership model that supports mixed content with per-item tiers and that ties access strictly to confirmed payment.
#H1#2.4 Selected Boundary for Proposed Solution
#P#The proposed solution implements a focused set of functions drawn from the gaps above. It gives each creator a separate membership space with Free, Basic, and Premium tiers and lets a subscriber hold an independent relationship with every creator. It supports mixed content, since a creator can publish videos, articles, and downloadable files and mark the required tier for each item. It ties access to payment by starting a Stripe Checkout session for paid tiers and granting paid access only after a signed webhook confirms the payment, which keeps billing and access in step. It protects files by serving them as access-checked attachments and by counting downloads against a monthly quota. It also provides administrative control over users, content, payments, and settings, so the platform can be kept healthy.
#P#Some functions are left outside the boundary of this project, for clear reasons. The system does not handle creator payouts or revenue sharing, since it runs Stripe on a single platform account and focuses on the membership and access model rather than on money movement to creators. It does not offer a single plan that unlocks every creator at once, because access is deliberately kept per creator. It runs against Stripe test mode and does not include production hosting or an automated test suite, as these fall beyond the scope of the current work and are noted as future improvements.
#TITLE#CHAPTER 3#SYSTEM REQUIREMENTS AND SPECIFICATIONS
#P#This chapter describes what the system is required to do and the parts it is built from. It sets out the system specification, the main modules that divide the work into separate units, and the functional and non-functional requirements that the software must meet.
#P#The chapter is organised into four sections. Section 3.1 gives the overall system specification. Section 3.2 describes the system modules. Section 3.3 lists the functional requirements or software features, and Section 3.4 describes the non-functional requirements together with how each one is measured.
#H1#3.1 System Specification
#P#The system is a web application with a server side and a browser side that share the same codebase through the Next.js framework. The server side holds the application logic, the access checks, and the connections to external services, while the browser side renders the pages and forms. Data is stored in a PostgreSQL database that holds seventeen tables covering users, creators, subscribers, plans, content, subscriptions, payments, notifications, analytics, contacts, and platform settings. External services provide three supporting functions, namely authentication through Clerk, billing through Stripe, and file storage through Cloudflare R2. The application enforces its rules on the server so that a request from the browser cannot bypass an access check, and it keeps a single source of truth for tier limits so that both the interface and the server agree on what each tier allows.
#P#The database schema is grouped by purpose so that each concern stays in its own set of tables. Identity is held in the user profile, creator profile, and subscriber profile tables, along with small tables for creator and subscriber preferences. The catalogue is held in the plan, plan feature, and content tables, where each content row carries its required tier and its links to stored media. Billing is held in the subscription and payment tables, where each subscription is unique for a subscriber and creator pair. Supporting data sits in the notification, analytics, contact, and platform settings tables. The content model supports three types, namely video that is uploaded or linked from an external source, articles written as text, and files stored as PDF, ZIP, or RAR. File sizes are limited on both the interface and the server, with images capped at eight megabytes, video at five hundred megabytes, and downloadable files at two hundred megabytes, so that oversized uploads are rejected early.
#H1#3.2 System Modules
#P#The system is divided into modules so that each area of work is handled by a separate, self-contained unit. This separation keeps the code easier to maintain and lets each module be reasoned about on its own. The main modules are authentication and role management, the creator workspace, subscription and billing, content access and downloads, administration, and notifications.
#H2#3.2.1 Authentication and Role Management
#P#This module handles sign-up, email verification, sign-in, Google sign-in, and password reset through Clerk. It assigns each user a role of subscriber or creator, and it recognises an administrator through an email allowlist held in the server configuration. Middleware checks every protected route and redirects a user who does not hold the required role. The module keeps the user's role and account status available to the rest of the system so that access checks elsewhere can rely on it.
#H2#3.2.2 Creator Workspace and Content Management
#P#This module gives a creator the tools to build and manage their space. A creator can publish three kinds of content, namely video that is either uploaded or linked from an external source, articles written as text, and downloadable files in PDF, ZIP, or RAR form. Each item is given a required tier of Free, Basic, or Premium and a status of draft, published, or archived. The module also lets a creator manage plans and view subscribers, revenue, and analytics for their own space.
#H2#3.2.3 Subscription and Billing
#P#This module manages the relationship between a subscriber and a creator. A free follow creates a free membership record for that subscriber and creator pair. A paid tier starts a Stripe Checkout session, and the resulting subscription record is written or updated only when Stripe sends a signed webhook confirming the change. The module records payments, supports cancellation that keeps access until the end of the paid period, and connects subscribers to the Stripe Customer Portal so they can manage cards and invoices.
#P#Each subscription carries a status that follows the Stripe lifecycle, namely active, trialing, past due, canceled, and expired. An active or trialing subscription grants the tier it was bought for. When a payment is late, the subscription moves to past due, and the system keeps access for a short grace window rather than cutting it off at once, so that a temporary card problem does not lock out a paying member. When a subscriber cancels, the subscription is marked to end at the close of the current period, and access continues until that date before it drops back to the free level. These rules are driven by the signed webhook events, so the stored status always follows what Stripe reports rather than a guess made by the interface.
#H2#3.2.4 Content Access and Downloads
#P#This module decides whether a subscriber may open or download a given item. It compares the required tier of the item against the subscriber's current tier for the owning creator, using the order Free, then Basic, then Premium. Files are never given to the browser as public links. Instead the server streams them as attachments after the access check, and it counts each download against a monthly quota that depends on the subscriber's tier for that creator.
#P#The quota is counted over a rolling window of thirty days for each subscriber and creator pair, so the count resets gradually rather than all at once on a fixed calendar date. The Free tier allows a small fixed number of downloads in that window, the Basic tier allows a larger number, and the Premium tier removes the limit for that creator. Before a file is streamed, the server checks both the tier and the remaining quota, and it refuses the download if either check fails. Because the check and the stream happen on the server, and because the file is delivered as an attachment tied to a single request, a subscriber cannot copy a plain link and share it with someone who has not paid.
#H2#3.2.5 Administration
#P#This module gives an administrator oversight of the whole platform. An administrator can view and manage users, creators, subscribers, content, plans, subscriptions, and payments. Administrative actions include suspending or restoring an account, cancelling or reactivating a subscription through Stripe, refunding or retrying a payment, and turning maintenance mode on or off. When maintenance mode is on, the public site shows a maintenance page while administrators keep access so they can turn it off again.
#H2#3.2.6 Notifications
#P#This module keeps users informed through an in-app inbox. It records notices about renewals, payments, content, account changes, and system messages, and it marks each notice as read or unread. Notices are delivered inside the application rather than through email campaigns, which keeps the message history in one place for each user.
#H1#3.3 Functional Requirements/Software Features
#P#The functional requirements describe what the system must do. They follow directly from the project scope and objectives, and they cover account handling, membership, content access, and administration. The main features are described below.
#H2#3.3.1 Account Registration and Sign-in
#P#The system must let a visitor create an account, verify an email address, and sign in, with support for Google sign-in and password reset. It must assign a role at sign-up and route each user to the correct area based on that role.
#H2#3.3.2 Following and Subscribing to a Creator
#P#The system must let a subscriber follow a creator for free and pay for a Basic or Premium tier through Stripe Checkout. It must record the membership for the specific subscriber and creator pair and must grant paid access only after payment is confirmed.
#H2#3.3.3 Tier-Based Content Access
#P#The system must compare each item's required tier against the subscriber's tier for the owning creator and must allow access only when the subscriber's tier is equal to or higher than the required tier. It must show previews to the public without granting full access.
#H2#3.3.4 Protected File Downloads with Quota
#P#The system must serve files as access-checked attachments and must count each download against a monthly quota set by the subscriber's tier. It must stop a download that would exceed the quota.
#H2#3.3.5 Creator Content and Plan Management
#P#The system must let a creator publish video, article, and file content, set the required tier and status for each item, and manage the Free, Basic, and Premium plans for their space.
#H2#3.3.6 Administrative Oversight
#P#The system must let an administrator manage users, content, plans, subscriptions, and payments, suspend or restore accounts, act on subscriptions and payments through Stripe, and control maintenance mode.
#H2#3.3.7 In-App Notifications
#P#The system must record notices for each user about renewals, payments, new or locked content, account changes, and system messages, and it must let the user mark a notice as read. It must show unread notices so the user can see recent activity without leaving the application.
#H1#3.4 Non-Functional Requirements
#P#The non-functional requirements describe how well the system performs its work. Each requirement below states why it matters for this system and how it can be measured.
#H2#3.4.1 Security
#P#Security matters because the system holds paid content and payment-related records. Access is checked on the server for every protected route and every gated item, files are served only as access-checked attachments, and paid access is written only after a signed Stripe webhook. Security can be measured by confirming that a signed-out or lower-tier user cannot reach a protected item or file in testing, with a target of zero successful bypasses across the tested cases.
#H2#3.4.2 Usability
#P#Usability matters because subscribers and creators are not expected to be technical. The interface presents clear paths for following, subscribing, and opening content, and it shows the current tier and remaining download quota. Usability can be measured by whether a new user can complete sign-up, follow a creator, and open a free item without help, with a target of completion in a single attempt for a first-time user.
#H2#3.4.3 Reliability
#P#Reliability matters because billing state must stay in step with access state. The system treats a payment as complete only after Stripe confirms it, and it fails safely when a service is not available, for example by showing that checkout is not ready rather than granting access. Reliability can be measured by the share of tested billing events that produce the correct access outcome, with a target of correct handling for every tested event.
#H2#3.4.4 Performance
#P#Performance matters because pages should feel quick to use. The system keeps a single source of truth for tier limits and reads membership and catalogue data through indexed database queries. Performance can be measured by the time to load the main library and subscription pages under normal development conditions, with a target of a response that feels immediate for a single active user.

#TITLE#CHAPTER 5#SYSTEM TESTING AND VALIDATION
#P#This chapter describes how the system was tested and what the tests showed. It explains the testing approach, the techniques used, the test cases designed for the main features, and the results observed when the tests were run.
#P#The chapter is organised into four sections. Section 5.1 introduces system testing and its importance. Section 5.2 describes the testing techniques used. Section 5.3 presents the test cases and their results, and Section 5.4 discusses the non-functional requirements and how they were measured.
#H1#5.1 System Testing
#P#System testing checks that the finished parts of the software work together and meet the requirements. It matters because a membership platform must protect paid content and must keep billing and access in step, and a single missed check can either block a paying member or expose paid content. The system was tested by hand on a development machine, using Stripe test mode, by running the application and exercising each main workflow as a real user would. The overall result of this testing was that the tested workflows behaved as expected, which supports the objectives of secure access and correct billing.
#P#The tests were run in a controlled environment that stood in for real use. The application ran locally against a PostgreSQL database, Stripe ran in test mode with test cards, and the Stripe command line tool forwarded signed webhook events to the local server so that the payment flow could be exercised end to end. Separate accounts were created for a subscriber, a creator, and an administrator, so that each role could be tested with the access it is meant to have. This setup made it possible to check the full path from sign-up through paid access, cancellation, and administration without spending real money or exposing real user data.
#H1#5.2 Testing Techniques
#P#Two testing techniques were used, namely black box testing and functional testing. Both were carried out manually, since the project does not include an automated test suite.
#H2#5.2.1 Black Box Testing
#P#Black box testing checks the system through its interface without looking at the internal code. It was chosen because the most important behaviour of this system, such as whether a lower-tier subscriber is refused a Premium file, is best judged from the outside. Each case was carried out by signing in as the relevant user, performing the action through the interface, and comparing the result with the expected outcome. The results matched the expected outcomes for the tested cases.
#H2#5.2.2 Functional Testing
#P#Functional testing checks that each feature does what the requirements say. It was chosen because the requirements in Chapter 3 map directly to features that can be exercised one by one, such as following a creator, paying for a tier, and downloading a file within the quota. Each feature was run through its normal path and through at least one failure path, such as a cancelled payment, and the observed behaviour agreed with the requirement.

#TITLE#CHAPTER 6#CONCLUSION
#P#This chapter concludes the report. It first draws together what the project achieved, and it then discusses the limits of the current system and the work that can be done in the future.
#H1#6.1 Conclusion
#P#The Advanced Subscription and Membership Platform set out to build a per-creator membership model where access is tied to confirmed payment and where each creator keeps a separate space. The finished system meets that goal for the defined scope. It supports sign-up and role handling through Clerk, per-creator Free, Basic, and Premium tiers, paid checkout through Stripe with access written only after a signed webhook, mixed content with per-item tiers, protected file downloads with a monthly quota, and administrative oversight of users, content, payments, and settings. Manual functional and black-box testing of these workflows produced the expected results, which shows that the access rules and the billing flow work together as intended. The project therefore demonstrates a complete and working membership service from sign-up through paid access and administration.
#P#Beyond the working features, the project met its wider aim of showing how several separate concerns can be joined into one clear service. Authentication, billing, storage, and access control each came with its own rules and its own external service, and the main work of the project was to make them agree with one another rather than to build any one of them alone. The design keeps a single source of truth for tier limits, checks access on the server, and writes paid access only after a confirmed payment, and these three choices together explain why the tested behaviour stayed correct. The result is a system that a small creator could use in practice and that also serves as a clear study of the membership model it was built to explore.
#H1#6.2 Limitations and Future Work
#P#The current system has clear limits. It runs against Stripe test mode and a single database, it has no automated test suite, and it does not handle creator payouts or a single plan that unlocks every creator at once. Its testing was manual, so it does not yet have repeatable automated checks. These limits can be addressed as future work. An automated testing layer would make checks repeatable and would catch regressions early. Support for creator payouts would let the platform move money to creators rather than only collecting it on one account. Production hosting, wider analytics, and a review of performance under many users would prepare the system for real use. With these additions, the platform could grow from a working project into a service ready for a live audience.
